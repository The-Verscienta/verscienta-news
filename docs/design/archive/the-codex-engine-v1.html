01

principles

A backend has a design language too. Not type and color — contracts, data shapes and failure modes — but the same discipline: a small set of opinions, applied everywhere, so the system is predictable before it is clever.

i

contract before code

The API shape is the product surface. Design the contract first and implement behind it; the wire format outlives every rewrite of what sits underneath it.

ii

one grammar

Every endpoint reads the same — plural nouns, cursor pages, UTC timestamps, opaque sortable IDs. Consistency beats cleverness; a developer should be able to guess the next route.

iii

boring on purpose

Postgres until it genuinely hurts. Exotic stores earn their place with evidence, not enthusiasm. The interesting parts of the product should live in the product, not the plumbing.

iv

everything is an event

State changes emit events; expensive reads are projections off the log. The append-only log is the source of truth for fan-out, search, notifications and audit.

v

fail loud, fail typed

Every error is a typed envelope with a stable code and a trace id. Clients switch on the code, humans read the title, and nothing ever leaks a stack trace or a raw 500.

vi

budgets are law

Latency, payload size and rate limits are named tokens, enforced at the edge — not numbers in a wiki that everyone has quietly stopped meeting.

02

the contract

If type is the grammar of the front-end, the API is the grammar of the back. REST over HTTP/2 is the spine: resources are nouns, behaviour is the verb, and every route is shaped the same so the surface is learnable from any single endpoint.

resource grammar

patternmethodmeaning
/v1/articlesGETlist, cursor-paged
/v1/articlesPOSTcreate (idempotency-key)
/v1/articles/{id}GET · PATCH · DELETEread · partial update · remove
/v1/users/{id}/feedGETassembled timeline, cursor-paged
/v1/posts/{id}/reactionsPOST · DELETEadd · remove a reaction
/v1/posts/{id}/commentsGET · POSTthread, cursor-paged

Nesting stops at one level — /posts/{id}/comments, never /users/{id}/posts/{id}/comments/{id}/replies. Deeper relationships are queried by id, not by URL archaeology.

conventions — the rules every route obeys

concernrule
identifiersULID — opaque, sortable, no leaked sequence
timestampsISO-8601, UTC, always; clients localize
paginationopaque cursor + limit; never offset
versioning/v1 in path; new version for breaking change
writesIdempotency-Key header; safe to retry
cachingETag + If-None-Match → 304

the envelope — every list looks the same

GET /v1/users/u_01J.../feed?limit=20 200 OK ETag: "9f2a..." { "data": [ { "id": "po_01J...", "type": "post", "...": "..." } ], "page": { "next": "eyJjdXJzb3IiOiI...", "has_more": true }, "meta": { "trace_id": "tr_01J..." } }

A REST spine stays cacheable and boring. A thin GraphQL gateway may sit in front for the read-heavy feed, but it composes these same resources — it never becomes a second, contradictory contract.

05

the publishing pipeline

How a story goes from a draft to a million feeds. The write path is short and synchronous — validate, persist, emit — and everything expensive happens off the event, so publishing never waits on fan-out.

the write path — synchronous, fast

01validateschema, length, ownership
02persistinsert into postgres, status = draft/live
03emitpublish content.published to the log
04respond201 + the created resource

off the event — async, parallel, retryable

consumers of content.published
moderationscan, score, hold or clear
indexingwrite to the search index
mediatranscode, generate variants
fan-outpush into follower timelines
notificationsalert followers & mentions

Each consumer is independent and idempotent — replaying the same event twice is harmless. A slow transcoder can never block indexing, and a failed notification never un-publishes the article. Ordering is guaranteed per resource, not globally.

06

graph & feed

The social half. Follows are edges; the timeline is the hardest read in the product. The engine uses the canonical answer: fan-out-on-write for the many, fan-out-on-read for the few — because the celebrity problem is a different problem.

feed generation — a hybrid by follower count

on write — normal accounts
new post → event
fan-out worker
prepend id into each follower's redis timeline
on read — high-follower accounts (above a threshold)
reader requests feed
merge stored timeline + pull recent from followed celebrities
redis + postgres

Writing a celebrity's post into 50M timelines is wasteful; their followers pull at read time instead and merge. Everyone else is fanned out on write so their feed is a single Redis range read. The threshold is a token, tuned, not guessed.

interactions

thingstoreshape
followspostgres edges + redis counts(follower, followee, created_at)
commentspostgres, materialized paththreaded, depth-capped, collapsible
reactionsredis counters, postgres durableeventually-consistent counts
trendingsearch / analytics tierwindowed counts, decayed

Counters live hot in Redis and are reconciled against Postgres on a schedule — the like count can lag by a second, and that is a deliberate trade, not a bug. Comment threads cap their depth and collapse, exactly like the front-end's thread component.

07

events & realtime

This is the engine in motion. The append-only log is the spine of everything asynchronous — fan-out, indexing, notifications, webhooks — and it is also how the product reaches the client in real time, without anyone polling.

delivery guarantees

propertyrule
deliveryat-least-once — consumers must be idempotent
orderingper partition key (per resource), not global
identityevery event carries a ULID + trace id
retriesexponential backoff + jitter, capped
poisondead-letter after N attempts, alert
realtimews/sse gateway tails the log, pushes to clients

Workers consume topics — moderation, indexing, fan-out, notifications, webhooks — and a WebSocket gateway subscribes to the same log to push live notifications, feed updates and trending. One log, many readers; no consumer can slow another.

backpressure — the engine yields gracefully

Just as the front-end honours prefers-reduced-motion, the back-end honours load. When a queue depth or latency budget is breached, the edge sheds — non-critical work degrades first (delayed fan-out, deferred indexing), reads stay up, and clients get a typed 503 with Retry-After rather than a hang. Degrade, never collapse.

08

do · don't

do
  • Design the contract first; implement behind it.
  • Cursor-paginate everything; keep cursors opaque.
  • Take an Idempotency-Key on every write.
  • Return typed errors with a stable code and trace id.
  • Emit an event on every state change.
  • Do expensive work off the event, idempotently.
  • Enforce budgets (latency, payload, rate) at the edge.
  • Use sortable opaque IDs (ULID) and UTC timestamps.
don't
  • Offset-paginate at scale, or expose row counts as IDs.
  • Return bare 500s or leak stack traces and DB errors.
  • Fan-out-on-write to a celebrity's millions of followers.
  • Make synchronous cross-service calls for non-critical work.
  • Run unbounded queries with no limit or timeout.
  • Ship breaking changes without a new version.
  • Trust client timestamps or client-supplied IDs blindly.
  • Let a slow consumer block the write path.

tokens

The engine has tokens too — not color and space, but budgets, limits and TTLs. Named, versioned, and enforced in code, so "fast" and "fair" mean specific numbers rather than good intentions. They ship as codex-backend-tokens.json.
