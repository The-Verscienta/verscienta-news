the engine

The same design language, pointed inward — and built on the BEAM. The domain is modelled once in Ash; LiveView renders it, PubSub makes it live, and Oban does the heavy lifting off to the side. One declarative source of truth, many faces.

01

principles

The BEAM hands you concurrency, isolation and distribution for free; Ash hands you a place to put the domain. The discipline is to declare the system once and let the framework generate the rest, rather than hand-rolling the same rules in five layers.

i

the resource is the truth

Model the domain once as Ash resources — attributes, relationships, actions, policies. LiveView, the JSON:API and GraphQL are all generated from it; there is never a second, drifting definition.

ii

declare, don't hand-roll

Validations, authorization, aggregates and side effects live on the resource as data, not scattered across controllers and contexts. Business rules have one home.

iii

boring on purpose

Postgres via AshPostgres; Oban (also Postgres) for jobs; PubSub for realtime. No Redis, no Kafka, no extra infrastructure until the BEAM genuinely can't carry it.

iv

let it crash, supervised

Each connection is a LiveView process, each job an Oban process — isolated and restarted by a supervisor. A bad request crashes one process, not the node.

v

the change is the event

Every Ash action emits a notification over PubSub. LiveViews react and re-render; durable consumers pick it up as Oban work. State change and event are the same act.

vi

fail typed

Ash returns structured error classes — invalid, forbidden, not_found. LiveView turns them into form errors, the JSON:API into JSON:API errors. Same failure, many faces, no bare 500.

02

the domain

Where the front-end's grammar is type, the back-end's grammar is the Ash resource. Attributes, relationships, actions and policies are declared in one place — and that one declaration becomes the LiveView boundary, the JSON:API, the GraphQL schema, and the authorization layer at once.

one resource — the single source of truth

defmodule Codex.Feed.Post do use Ash.Resource, domain: Codex.Feed, data_layer: AshPostgres.DataLayer, authorizers: [Ash.Policy.Authorizer], notifiers: [Ash.Notifier.PubSub] attributes do uuid_v7_primary_key :id # sortable, opaque attribute :body, :string, allow_nil?: false, constraints: [max_length: 280] attribute :state, :atom, constraints: [one_of: [:draft, :published]], default: :draft timestamps() end relationships do belongs_to :author, Codex.Accounts.User has_many :comments, Codex.Feed.Comment end actions do defaults [:read] read :timeline do # keyset, not offset pagination keyset?: true, default_limit: 20 end update :publish, change: set_attribute(:state, :published) end policies do policy action_type(:read) do authorize_if expr(state == :published or author_id == ^actor(:id)) end policy action(:publish) do authorize_if actor_present() end end pub_sub do module CodexWeb.Endpoint prefix "post" publish :publish, ["feed", :author_id] # broadcast on publish end end

That one file is the contract. The web layer never re-implements its rules — it calls actions.

one definition, many interfaces

LiveView · code interface AshJsonApi · JSON:API AshGraphql · schema AshPaperTrail · audit AshStateMachine · draft→published

# a policy failure raises Ash.Error.Forbidden case Codex.Feed.publish(post, actor: user) do {:ok, post} -> {:noreply, stream_insert(socket, :posts, post, at: 0)} {:error, %Ash.Error.Forbidden{}} -> {:noreply, put_flash(socket, :error, "Not allowed")} {:error, %Ash.Error.Invalid{} = err} -> {:noreply, assign(socket, form: to_form(err))} # field errors end

04

architecture

The shape is OTP, not a service mesh. A browser holds a WebSocket to a LiveView process; that process talks to Ash, which talks to Postgres. Oban runs jobs beside it, PubSub spans the cluster, and a supervision tree holds it all up.

05

the publishing pipeline

Publishing a post is one Ash action. It validates, checks policy, persists, and emits a notification — synchronously and fast. Everything expensive is an Oban job triggered off that action, so the author waits on none of it.

the action — synchronous, transactional

01validatechangeset + resource constraints
02authorizepolicy check on :publish
03persiststate machine draft → published
04notifyPubSub broadcast + enqueue jobs

off the action — oban queues, parallel & retryable

oban workers triggered on :publish (via AshOban)
moderationscan, score, hold or clear
indexingupdate search
mediatranscode, variants
fanoutwrite follower timelines
notifyalert followers & mentions
defmodule Codex.Feed.FanoutWorker do use Oban.Worker, queue: :fanout, max_attempts: 5, unique: [period: 60, keys: [:post_id]] # idempotent enqueue @impl true def perform(%Oban.Job{args: %{"post_id" => id}}) do # write id into each follower's timeline, broadcast via PubSub :ok end end

Each worker is independent and idempotent — Oban's uniqueness stops double-enqueues, and a failed job retries with exponential backoff before landing in discarded. A slow transcoder never blocks indexing; a failed notification never un-publishes the post.

the live feed — streams, not assigns

def mount(_params, _session, socket) do if connected?(socket), do: Phoenix.PubSub.subscribe(Codex.PubSub, "feed") page = Codex.Feed.timeline!(actor: socket.assigns.current_user, page: [limit: 20]) {:ok, stream(socket, :posts, page.results)} end def handle_info({:post_published, post}, socket) do # PubSub {:noreply, stream_insert(socket, :posts, post, at: 0)} # live, no refresh end def handle_event("load_more", %{"cursor" => after}, socket) do page = Codex.Feed.timeline!(actor: socket.assigns.current_user, page: [after: after, limit: 20]) # keyset {:noreply, stream(socket, :posts, page.results)} end

Streams keep the collection in the DOM, not in server memory, so a 10,000-post feed costs the LiveView process almost nothing. Counts come from Ash aggregates; trending is an Oban cron job over a decaying window. Comment threads are an Ash resource, depth-capped and collapsible — the mirror of the front-end's thread component.

07

realtime

This is the engine in motion, and it splits cleanly in two: PubSub for the ephemeral and live, Oban for the durable and guaranteed. Knowing which is which is the whole correctness story.

two channels, two guarantees

phoenix.pubsuboban
forlive UI updateswork that must happen
deliverybest-effort, in-memoryat-least-once, durable
if a node dropsmessage is lostjob survives, retries
idempotencyn/a (transient)unique keys on enqueue
orderingper-topic, best-effortper-queue, with priorities
sourceAsh.Notifier.PubSubAshOban triggers

Never use PubSub for something that must happen. A like-count tick or a "new posts" banner is PubSub — if a browser misses it, the next read corrects it. A fan-out, an email, a charge is Oban — it retries until it succeeds or is explicitly discarded. Ash's notifier feeds the first; AshOban feeds the second.

backpressure — the engine yields, it doesn't collapse

Just as the front-end honours prefers-reduced-motion, the back-end honours load. Oban queues have fixed concurrency, so a flood of jobs queues rather than overwhelming Postgres. A LiveView process that crashes is restarted by its supervisor with the client none the wiser. Under real strain the edge sheds writes with a typed error and keeps reads alive — degrade, never collapse.

08

do · don't

do
  • Model the domain once as Ash resources; generate the rest.
  • Declare policies on the resource; let every action enforce them.
  • Go through actions, never raw Ecto, from the web layer.
  • Keyset-paginate and render collections with LiveView streams.
  • Broadcast changes with the Ash PubSub notifier.
  • Put work that must happen in Oban, unique & retried.
  • Let it crash — supervise, don't defensively rescue.
  • Use uuid_v7 keys and Ash aggregates for counts.
don't
  • Re-implement resource rules in LiveViews or controllers.
  • Reach around Ash with raw Ecto in the web layer.
  • Trust PubSub for durable delivery — that's Oban's job.
  • Hold big collections in assigns — use streams.
  • Offset-paginate a feed, or block on slow work in handle_event.
  • Fan-out-on-write to a celebrity's millions of followers.
  • Scatter authorization checks across the web layer.
  • Swallow Ash errors — render them typed.
